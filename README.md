# Clinic Appointment Booking API

A Spring Boot backend for a small clinic: doctors publish time slots, patients book, cancel and reschedule them.
The point of the project is one hard, real problem: **two patients must never be able to book the same slot,
even when their requests arrive at the same instant.**

## The problem

Small clinics often take bookings by phone, WhatsApp or a shared spreadsheet. When two people grab the same slot at
the same time, the doctor ends up double-booked, one patient is turned away at the door, and the receptionist
spends the day sorting it out. No-shows add to the waste because nobody reminds patients.

This API is a small-scale version of the fix:

- a slot can be booked by **exactly one** patient, guaranteed by the database rather than by hope;
- retrying a request (bad network, double-click) **never** creates a second booking;
- cancelling and rescheduling follow clear rules and are atomic;
- patients are reminded before their appointment.

## Features

| Area | What it does |
|---|---|
| Auth | Register / login, JWT (HS256), roles `PATIENT` and `ADMIN` |
| Doctors & slots | Admin adds doctors and generates slots (e.g. 09:00-13:00 in 30-minute pieces). Anyone can browse doctors and free slots |
| Booking | Atomic, race-free booking with optional `Idempotency-Key` header |
| Cancel | Allowed until 2 hours before the start (configurable). Cancelling twice is harmless |
| Reschedule | Moves to another slot of the **same doctor** in one transaction; if the new slot is taken you keep the old one |
| Reminders | A scheduled job finds appointments starting within 24 h and reminds each patient once |
| Errors | One consistent JSON format (RFC 7807 `application/problem+json`) with correct 400/401/403/404/409/422 codes |
| Docs | Swagger UI at `/swagger-ui.html` |

### 3. Try it

**Easiest: Swagger UI.** Open `/swagger-ui.html`, call `POST /api/auth/register`, copy the `token` from the response,
click **Authorize** (top right), paste the token, and every request will be authenticated.

**Or with curl** (bash; use Swagger UI on Windows):

```bash
BASE=http://localhost:8080

# 1) Register a patient. The response contains a JWT "token".
curl -s -X POST $BASE/api/auth/register -H "Content-Type: application/json" \
  -d '{"name":"Asha","email":"asha@example.com","password":"Passw0rd!"}'
export TOKEN=<paste the token here>

# 2) Browse (public): doctors, then a doctor's free slots on a date (use tomorrow's date, YYYY-MM-DD)
curl -s $BASE/api/doctors
curl -s "$BASE/api/doctors/1/slots?date=YYYY-MM-DD&onlyAvailable=true"

# 3) Book slot 1. Idempotency-Key makes retries safe.
curl -s -i -X POST $BASE/api/appointments \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -H "Idempotency-Key: my-first-booking" -d '{"slotId":1}'
#    -> 201 Created
#    Run the exact same command again -> 200 OK with "Idempotent-Replayed: true" and the SAME appointment id.

# 4) Register a second patient and book slot 1 again -> 409 Conflict ("Slot is no longer available").

# 5) Reschedule appointment 1 to slot 2 (same doctor). The old appointment becomes CANCELLED and a new one is returned.
curl -s -X POST $BASE/api/appointments/1/reschedule \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"newSlotId":2}'

# 6) List my appointments, then cancel the new one (use the id from step 5)
curl -s $BASE/api/appointments/me -H "Authorization: Bearer $TOKEN"
curl -s -X POST $BASE/api/appointments/2/cancel -H "Authorization: Bearer $TOKEN"
```

Admin actions (log in as the admin, then use that token): add a doctor and generate slots.

```bash
curl -s -X POST $BASE/api/auth/login -H "Content-Type: application/json" \
  -d '{"email":"admin@clinic.com","password":"Admin@123"}'
export ADMIN=<paste the admin token>

curl -s -X POST $BASE/api/doctors -H "Authorization: Bearer $ADMIN" -H "Content-Type: application/json" \
  -d '{"name":"Dr. Meera Iyer","specialization":"Pediatrics"}'

curl -s -X POST $BASE/api/doctors/3/slots -H "Authorization: Bearer $ADMIN" -H "Content-Type: application/json" \
  -d '{"date":"YYYY-MM-DD","startTime":"10:00","endTime":"12:00","slotMinutes":20}'
```

## How it works (the design decisions)

### 1. Preventing double-booking: an atomic compare-and-set in the database

The naive approach is "check if the slot is free, then insert a booking". Between the check and the insert there is
a gap, and in that gap other requests also see "free". That is the race condition (reproduced on purpose in
`NaiveCheckThenActRaceDemoTest`).

The fix is to make the check and the claim **one atomic statement** that the database executes:

```sql
UPDATE slots SET status = 'BOOKED', version = version + 1
WHERE id = ? AND status = 'AVAILABLE';
```

The database serialises concurrent updates to the same row. The first transaction changes 1 row; every other one
changes **0 rows** and the service turns that into `409 Conflict`. The code is `SlotRepository.markBooked` and
`BookingService.claimSlot`.

Why this and not the alternatives:

| Option | Trade-off |
|---|---|
| **Atomic conditional UPDATE (used)** | Short transaction, no explicit locks, works the same on PostgreSQL and H2 |
| Pessimistic lock (`SELECT ... FOR UPDATE`) | Correct, but holds a row lock for the whole transaction and needs a lock-timeout strategy |
| Optimistic locking only (`@Version`) | Correct, but losers fail with exceptions at flush time; `@Version` is kept on `Slot` as a second safety net |
| Unique constraint on a booked slot | Needs a partial unique index, which H2 does not support (this project runs on both) |

### 2. Idempotency: retries never double-book

A client may send the same request twice (timeout and retry, double click). If the request carries an
`Idempotency-Key` header, `(patient, key)` is stored on the appointment with a unique constraint. A repeat with the
same key returns the **original** appointment (`200` + `Idempotent-Replayed: true`) instead of booking again.
A key is scoped to the patient. Reusing a key for a different slot returns the original appointment; a stricter
version could also compare the request body.

### 3. Atomic reschedule

Reschedule claims the **new** slot first, and only then cancels the old appointment and releases its slot, all in one
transaction. If the new slot was taken, the transaction rolls back and the patient keeps their original appointment.
There is no moment where they have neither (covered by `failedRescheduleKeepsTheOriginalAppointment`).

### 4. Business rules (all in `BookingService`)

- Cannot book a slot that has already started.
- Cancel/reschedule only until `clinic.cancellation-window-hours` (default 2) before the start.
- Reschedule only to another slot of the same doctor.
- Patients can only touch their own appointments; someone else's id returns `404`, not `403`, so ids cannot be probed.

### 5. Security

Stateless JWT auth. `JwtAuthFilter` reads `Authorization: Bearer <token>` and puts the user into the security
context; URL rules in `SecurityConfig` decide who can call what. Passwords are hashed with BCrypt. Login returns the
same error for "unknown email" and "wrong password". Admins can only be created by the startup seeder, never by
self-registration.

### 6. Database and migrations

The schema lives in `src/main/resources/db/migration/V1__init_schema.sql` (Flyway) and is written to run on both
PostgreSQL and H2. Hibernate never generates the schema. Constraints do real work: unique `(doctor, start_time)` for
slots, unique `(patient, idempotency_key)` for appointments, unique email for users.

### 7. Reminders

`ReminderScheduler` polls every minute; `ReminderService` finds `BOOKED` appointments starting in the next 24 h that
have `reminder_sent = false`, "sends" the reminder (it is logged, plug in an email/SMS provider here) and flips the
flag so nobody is reminded twice.

### 8. Time

All slot times are the clinic's local time (`clinic.timezone`, default `Asia/Kolkata`). One injected `Clock` is used
everywhere instead of `LocalDateTime.now()`, so time rules are easy to test.

## Known limitations and next steps

- Slot browsing is not cached. A Redis (or Caffeine) cache for availability would cut read load, with eviction on
  book/cancel.
- The reminder scheduler would send duplicates with several app instances. Add ShedLock or run it on one instance.
- Reminders are logged, not emailed. Plug in an email/SMS provider.
- No rate limiting, refresh tokens, pagination or password reset.
- Idempotency keys are not compared against the request body, and two truly simultaneous requests with the *same*
  key may see one `409` (a retry then returns the original).
- Slot times are timezone-naive local clinic time. Multi-timezone clinics would need `Instant`/`ZonedDateTime`.
